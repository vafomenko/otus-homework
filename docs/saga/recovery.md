# Восстановление после сбоя

Состояние саги, платежи и резервы сохраняются в PostgreSQL.
После перезапуска Orders фоновый worker продолжает обработку с последнего
сохранённого шага. Повтор запроса клиента для этого не требуется.

| Момент сбоя | Поведение |
|---|---|
| До записи заказа | Повтор POST с тем же ключом создаст один заказ |
| После записи заказа, до внешнего вызова | Worker выполнит сохранённый шаг |
| До commit участника | Локальная транзакция откатится; Orders начнёт компенсацию при ошибке вызова |
| После commit участника, до сохранения шага в Orders | Повтор команды с тем же orderId вернёт прежний результат без повторного эффекта |
| Потеря ответа участника при работающем Orders | Сага компенсирует также операцию с неизвестным результатом |
| Во время компенсации | Worker повторит незавершённый refund/release без двойного возврата |
| После сохранения итога, до доставки уведомления | Outbox повторит публикацию; Notifications подавит дубликат |

Одновременно заказ обрабатывает один координатор под advisory-блокировкой.
Перед каждым шагом он проверяет соединение. Бездействующая транзакционная
сессия ограничена 30 секундами, чтобы зависший процесс не удерживал блокировку
бессрочно. Запоздавшие команды после отмены не создают списание или резерв.

## Сроки и повторные попытки

Прямое выполнение ограничено двумя минутами (`deadline_at`). Просроченная
сага при следующей обработке начинает откат с причиной `saga_timeout`.
Неудачные компенсации повторяются с задержкой 1, 2, 4, 8, 16 и далее 30 секунд.
Состояние повторов сохраняется в БД и переживает перезапуск.

Пока участник недоступен, заказ остаётся `compensating`. `rejected` выставляется
после подтверждения всех компенсаций; срок прямого выполнения не обрывает
незавершённый откат. Восстановление требует сохранности БД/PVC и возвращения
доступности участников.

Worker выбирает до 100 готовых к повтору саг и обрабатывает до четырёх
одновременно. Отложенные попытки не блокируют выборку новых заказов.

## Диагностика

Клиент читает `GET /orders/{id}` до `paid` или `rejected`. Если ответ на создание
потерялся, исходный POST повторяется с прежними `Idempotency-Key` и телом.

```powershell
./scripts/inspect-sagas.ps1
kubectl --kubeconfig .local/kubeconfig-saga -n blt get deployments,statefulsets,pvc
kubectl --kubeconfig .local/kubeconfig-saga -n blt logs deployment/blt-saga-orders --since=10m
```

[Диагностический SQL](diagnostics.sql) показывает шаг, дедлайн,
`recovery_attempts`, `last_attempt_at`, `retry_count`, `next_attempt_at`
и `last_error`.

| Наблюдение | Действие |
|---|---|
| `undo_delivery_unavailable`, `undo_stock_unavailable`, `undo_payment_unavailable` | Восстановить указанный сервис и его БД; worker продолжит автоматически |
| Более пяти минут не меняется `last_attempt_at` | Проверить реплики Orders, доступность БД и логи recovery |
| Повторяется `recovery_error` | Найти исключение по orderId и исправить данные или конфигурацию |
| Миграции не проходят или PVC не Bound | Восстановить БД/хранилище и параметры подключения |

После исправления конфигурации Orders можно перезапустить:

```powershell
kubectl --kubeconfig .local/kubeconfig-saga -n blt rollout restart deployment/blt-saga-orders
kubectl --kubeconfig .local/kubeconfig-saga -n blt rollout status deployment/blt-saga-orders --timeout=120s
```

Перед ручным вмешательством сверяются платёж и резервы по orderId.
Итоговый статус должен соответствовать подтверждённым операциям участников.

## Тесты

```powershell
dotnet test tests/Blt.Saga.Tests/Blt.Saga.Tests.csproj
./scripts/test-saga-recovery.ps1
```

.NET-тесты моделируют остановку координатора после commit каждого из шести
шагов и проверяют восстановление worker, дедлайн, повторы и конкурентные вызовы.
Kubernetes-тест останавливает Delivery, перезапускает Billing и Warehouse,
принудительно завершает pod Orders и восстанавливает Delivery.
Новый процесс возвращает деньги и товар без повторного создания заказа.
